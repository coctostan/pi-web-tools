# Configurable fetch_content filter model

## Summary

`fetch_content({ prompt })` now uses the existing `filterModel` configuration field as the public way to choose the summarization/filter model. When `filterModel` is omitted, pi-web-tools preserves zero-config auto-detection using its built-in candidate list. Cache reads and writes are separated by the effective model identity so filtered answers from one model are not reused for another.

## Why this was built

Prompt-filtered fetches previously depended on auto-detected filter candidates. This made it difficult to choose a specific model for summarization/filtering and created cache-risk cases where an answer generated by one model could be reused before the effective model was known. The change makes model choice explicit through `filterModel` while preserving fallback behavior and raw-content safety.

## Public API surface

### `getConfig()`

Signature confirmed from `config.ts`:

```ts
export function getConfig(): WebToolsConfig
```

`getConfig()` reads `filterModel` from the configured web-tools JSON file and accepts it only when it is a string in `provider/model-id` format. Missing or malformed values return `undefined`.

### `resolveFilterModel()`

Signature confirmed from `filter.ts`:

```ts
export async function resolveFilterModel(
  registry: ModelRegistry,
  configuredModel?: string
): Promise<FilterModelResult>
```

When `configuredModel` is provided, it is parsed as `provider/model-id` and tried before auto-detect candidates. Malformed direct values return a structured failure reason before registry lookup.

### `filterContent()`

Signature confirmed from `filter.ts`:

```ts
export async function filterContent(
  content: string,
  prompt: string,
  registry: ModelRegistry,
  configuredModel: string | undefined,
  completeFn: CompleteFn,
  signal?: AbortSignal
): Promise<FilterResult>
```

`filterContent()` resolves the configured or auto-detected model, calls `complete(...)` with the resolved model and auth, and returns either filtered content plus the effective model ID or a structured fallback reason.

### `getFilterModelKeys()`

Signature confirmed from `filter.ts`:

```ts
export function getFilterModelKeys(configuredModel?: string): string[]
```

Configured mode returns a singleton cache-key list. Auto-detect mode returns the built-in candidate model IDs in auto-detect order.

## Behavior changes

- `filterModel` is validated as `provider/model-id`; malformed persisted config is ignored.
- Direct malformed configured-model strings passed to `resolveFilterModel()` return a structured malformed-config reason without registry/auth calls.
- Configured model cache hits now expose `details.filterModel`.
- Auto-detect mode skips early cache reads until filtering determines the effective model.
- Cache writes use the actual effective model returned from filtering.
- README documents `filterModel`, the required format, and omit-to-auto-detect behavior.
