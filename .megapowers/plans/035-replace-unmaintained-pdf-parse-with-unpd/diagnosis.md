# Diagnosis

## Root Cause

The PDF branch of `extractViaHttp` in `extract.ts` is bound at the source level (import + call sites) and at the dependency level (`package.json` + lockfile) to `pdf-parse@2.4.5`, an unmaintained CJS-shimmed package that bundles an old fork of `pdf.js` and is reported to eagerly read a sample fixture (`./test/data/05-versions-space.pdf`) at module-init time in some installs.

Evidence:

- `extract.ts:5` — `import { PDFParse } from "pdf-parse";` (static, top-of-file ESM import → side effects run at module load).
- `extract.ts:111,120,121,134` — the only consumer of `PDFParse`:
  ```ts
  let parser: InstanceType<typeof PDFParse> | null = null;
  ...
  parser = new PDFParse({ data: buffer });
  const parsed = await parser.getText();
  ...
  await parser?.destroy().catch(() => {});
  ```
- `package.json:62` — `"pdf-parse": "^2.4.5"` in `dependencies`.
- `package-lock.json:4787-4797` — pins `pdf-parse@2.4.5` with `bin/cli.mjs`.
- Installed package metadata: `node_modules/pdf-parse/package.json` resolves `main` to `dist/pdf-parse/cjs/index.cjs` — a CJS bundle interop'd into an otherwise ESM project, increasing the surface area where init-time `fs` reads run on import.
- `README.md:283` documents the user-visible contract this code path provides: "PDF text is extracted with `pdf-parse`. Corrupt, encrypted, empty, or oversized PDFs return a clear error." That contract is what must be preserved across the swap.

There is no runtime defect to attribute to a specific line; the defect is structural: the project's PDF extraction is coupled to an unmaintained, side-effect-prone dependency. The "wrong value" being traced is therefore a dependency identity (`pdf-parse` instead of `unpdf`), not a computed value.

## Trace

Symptom (per issue): unmaintained dependency w/ latent init-time fixture read on sandboxed FS.

Backward trace from runtime entry to source:

1. User-facing entry: `extractContent(url, signal)` — `extract.ts:222`.
2. `extractContent` calls `extractViaHttp(url, signal)` — `extract.ts:243`.
3. `extractViaHttp` decides PDF branch via `isPdf(contentType)` (`extract.ts:65,110`).
4. PDF branch: reads `arrayBuffer`, wraps in `Buffer`, then invokes the broken-by-association code:
   ```
   parser = new PDFParse({ data: buffer });    // extract.ts:120
   const parsed = await parser.getText();      // extract.ts:121
   ```
5. `PDFParse` resolves to the import at `extract.ts:5` → `node_modules/pdf-parse/dist/pdf-parse/cjs/index.cjs` (bundled pdf.js fork).
6. Module identity comes from `package.json:62` → `package-lock.json:4787` → registry tarball `pdf-parse-2.4.5.tgz`.

That is the full chain. The "correct → incorrect" transition is at step 6 (dependency choice) and propagates through step 5 (import).

## Affected Code

- `package.json:62` — `"pdf-parse": "^2.4.5"` must be removed; `unpdf` added.
- `package-lock.json:4787-4797` — will be regenerated by `npm install unpdf` / `npm uninstall pdf-parse`.
- `extract.ts:5` — replace import with `unpdf` named imports (`extractText`, `getDocumentProxy`).
- `extract.ts:109-136` — the PDF branch inside `extractViaHttp`. Specifically:
  - `109`: comment `// PDF: extract text via pdf-parse` → update wording.
  - `111`: `InstanceType<typeof PDFParse>` typing must be dropped (unpdf has no class to instantiate).
  - `120-121`: replace `new PDFParse({ data: buffer })` + `parser.getText()` with `getDocumentProxy(new Uint8Array(...))` + `extractText(pdf, { mergePages: true })`.
  - `122`: `parsed.text` is now possibly `string | string[]` depending on `mergePages`; with `mergePages: true` it's a single `string` — preserve current `.trim()` semantics.
  - `133-134`: drop the `parser?.destroy()` finally — unpdf has no destroy lifecycle on the proxy in the same shape.
- `extract.test.ts:183-259` — three PDF tests (valid / corrupt / oversized). Their `mockFetch`-only mocking strategy works against `pdf-parse` because `pdf-parse` accepts the raw bytes. Against `unpdf` they will need to either:
  - (a) feed real PDF bytes through unpdf (the "extracts text from PDF content-type" test already provides a minimal valid PDF; verify unpdf can parse it), and/or
  - (b) `vi.mock("unpdf", ...)` to stub `extractText`/`getDocumentProxy` deterministically.
- `README.md:283` — copy mentions `pdf-parse`; should be updated to `unpdf` (or generic phrasing).

## Pattern Analysis

**Working examples in this codebase that show the target shape:**

- The rest of `extract.ts` uses small, ESM-first, side-effect-free libraries with simple function calls — `@mozilla/readability`, `linkedom`, `turndown`, `p-limit`. None of them allocate resources requiring an explicit `destroy()`. The current `pdf-parse` block is the **only** place that uses a class + lifecycle pair (`new X` + `await x.destroy()`), and it's also the only place importing a CJS-built package.

**Differences between the working pattern and the broken one:**

| Aspect                  | Working pattern (rest of `extract.ts`) | Broken pattern (`pdf-parse`)                |
| ----------------------- | -------------------------------------- | ------------------------------------------- |
| Module format           | ESM                                    | CJS bundle interop'd into ESM project       |
| Surface                 | Pure functions                         | Class with `getText()` + `destroy()`        |
| Init-time side effects  | None                                   | Reported eager fixture file read            |
| Maintenance status      | Active                                 | Effectively unmaintained, old pdf.js fork   |
| Lifecycle in call sites | One call, no `try/finally`             | `new` + `try` + `finally` w/ `.destroy()`   |

**`unpdf` API alignment (verified from upstream docs):**

```ts
import { extractText, getDocumentProxy } from "unpdf";
const pdf = await getDocumentProxy(new Uint8Array(buffer));
const { totalPages, text } = await extractText(pdf, { mergePages: true });
```

This matches the issue's stated `{ text, totalPages }` shape and the pure-function pattern the rest of `extract.ts` already uses.

**Assumptions the current broken code makes that will not survive the swap:**

1. There is a class to type with `InstanceType<typeof PDFParse>` — `unpdf` exposes functions, not a class. (`extract.ts:111`)
2. The parser needs explicit teardown — `unpdf`'s proxy is garbage-collected. (`extract.ts:133-134`)
3. `getText()` always returns `{ text: string }` — `unpdf`'s `extractText` returns `text` typed as `string | string[]`; with `mergePages: true` it narrows to `string`.
4. Tests can pass raw bytes through `fetch` and let the library do its thing — true for both libraries; the tests' mocking strategy survives if real PDF bytes parse, or is replaced with `vi.mock("unpdf", ...)`.

## Risk Assessment

`extractViaHttp` is the sole caller of `PDFParse`. `extractContent` is the sole caller of `extractViaHttp`. `fetchAllContent` (`extract.ts:269`) wraps `extractContent` via `p-limit`. The blast radius is:

- **Direct dependents**: `extractContent`, `fetchAllContent`.
- **Downstream tool surface**: any registered tool that calls `extractContent` / `fetchAllContent` to extract a PDF URL (web fetch tools). Their return shape (`ExtractedContent` from `storage.js`) is unchanged, so callers are insulated **as long as**:
  - Error string for corrupt PDFs still satisfies `result.error contains "PDF"` (the existing test asserts `expect(result.error).toContain("PDF")` at `extract.test.ts:240`).
  - Empty-PDF error still satisfies the contract `"Failed to extract text from PDF: no readable text found"`.
  - Oversized PDF still short-circuits *before* invoking the library (already true at `extract.ts:104-107,116-118`).
- **Tests at risk**:
  - `extract.test.ts:183-213` (valid PDF) — needs unpdf to actually parse the hand-crafted minimal PDF, *or* needs `vi.mock("unpdf")`. The minimal PDF in the test is borderline (no compressed streams, single `Tj` op); real pdf.js may emit empty text on it. **High likelihood of needing a `vi.mock` switch.**
  - `extract.test.ts:215-243` (corrupt PDF) — currently asserts `error` contains `"PDF"`. Swap must preserve that substring. The current code path concatenates `Failed to extract text from PDF: ${msg}` (`extract.ts:132`), so this stays correct as long as that wrapper line is preserved.
  - `extract.test.ts:245-259` (oversized) — exercises the pre-library size guard (`extract.ts:105-107`), so library-agnostic; should pass untouched.
- **Bundle size / install footprint**: acceptance criterion requires verifying via `npm pack --dry-run` or `npm ls`. Risk is low (unpdf is zero-dependency, but ships its own pdf.js serverless bundle ~MBs); needs concrete measurement.
- **Init-time side effects**: acceptance criterion requires confirming the new library does no fixture file reads. `unpdf` upstream advertises zero deps and serverless-bundle pdf.js, but should be verified by scanning `node_modules/unpdf` post-install for any `test/data/*.pdf` reads at import.

No other code paths use PDF parsing, and `ExtractedContent`'s shape is library-agnostic, so the risk is well-bounded inside `extract.ts` + its tests + `README.md`.

## Fixed When

1. `package.json` no longer lists `pdf-parse` in `dependencies`; `unpdf` is present with a pinned semver range.
2. `package-lock.json` reflects #1 (no `node_modules/pdf-parse` entry after `npm install`).
3. `extract.ts` imports only `unpdf` for PDF text extraction; no references to `PDFParse` / `pdf-parse` remain anywhere in source.
4. The PDF branch of `extractViaHttp` (`extract.ts:110-136`) returns the same `ExtractedContent` shape (`{ url, title, content, error }`) it does today, with:
   - Success: non-empty `content`, `error: null`, `title` derived from `extractHeadingTitle(text.slice(0, 4096)) || titleFromUrl(url)`.
   - Empty extraction: `error: "Failed to extract text from PDF: no readable text found"`, `content: ""`.
   - Library-thrown error: `error` starts with `"Failed to extract text from PDF: "` so the existing test assertion `expect(result.error).toContain("PDF")` still passes.
   - Oversized: pre-library guard returns `error: "Response too large"` unchanged.
5. `extract.test.ts` PDF cases (`183-213`, `215-243`, `245-259`) pass against the new library — mocking strategy adjusted to `vi.mock("unpdf", ...)` (or real-parse where the hand-crafted PDF is sufficient).
6. `npm test` reports the full suite green (currently 26/26).
7. No fixture / sample PDFs are loaded by the PDF library at module import — confirmed by reading `node_modules/unpdf` package contents and/or its README claims; no `ENOENT`-style errors when running tests with a CWD that lacks `./test/data/`.
8. `README.md:283` mention of `pdf-parse` updated to reflect the new library (or made library-agnostic).
9. Install footprint check executed (`npm pack --dry-run` or `npm ls`) and recorded — acceptance criterion #5 from the issue.
