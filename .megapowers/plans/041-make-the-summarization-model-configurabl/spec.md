## Goal

Make the model used by `fetch_content({ prompt })` configurable through the existing `filterModel` setting, while preserving zero-config auto-detection, graceful raw-content fallback, and cache separation by effective model.

## Acceptance Criteria

1. `getConfig()` reads an optional `filterModel` value from `~/.pi/web-tools.json` or the configured `PI_WEB_TOOLS_CONFIG` path.

2. `getConfig()` accepts `filterModel` only when it is a string in `provider/model-id` form and returns `undefined` when the field is missing or malformed.

3. `filterModel` remains the only public config field for this behavior; no `summarizationModel` alias or replacement is introduced.

4. `resolveFilterModel(registry, configuredModel)` attempts the configured `provider/model-id` first when `configuredModel` is provided.

5. When the configured model exists in Pi’s model registry and `getApiKeyAndHeaders` returns usable auth, `filterContent(...)` uses that model for the `complete(...)` filtering call.

6. When no `filterModel` is configured, `resolveFilterModel(...)` preserves the existing auto-detect candidate order from `AUTO_DETECT_MODELS`.

7. When the configured model is missing, malformed, unavailable, or lacks usable auth, filtering returns a structured failure reason instead of throwing or aborting the fetch.

8. When filtering fails because no model is available, model auth fails, the model errors, or the model returns an invalid/too-short response, `fetch_content({ prompt })` returns raw fetched content with a warning rather than failing the fetch.

9. Prompt-filtered research-cache lookup and write paths key cached answers by the effective filter model identity, so answers generated by one model are not reused for a different configured or auto-detected model.

10. Successful filtered `fetch_content({ prompt })` results expose the selected filter model in result details as `filterModel`.

11. README configuration docs show `filterModel`, describe it as the model used by `fetch_content({ prompt })`, show the `provider/model-id` format, and state that omitting it preserves auto-detection.

12. Automated tests cover configured-model config loading, missing/malformed config behavior, configured-model selection, default auto-detection, unavailable configured-model fallback, filter failure raw-content fallback, successful result detail `filterModel`, and cache separation by model.

## Out of Scope

- Per-call model override parameters on `fetch_content`.
- UI or command support for changing the summarization/filter model.
- Changes to the filtering prompt or summarization semantics beyond model selection.
- Adding model providers outside Pi’s existing model registry/auth flow.
- Introducing `summarizationModel` or any other config alias for this slice.
- Broad refactors unrelated to `filterModel` configurability, fallback behavior, documentation, and tests.
- Expanded documentation of many provider-specific example models, beyond what is needed to explain the supported format.
